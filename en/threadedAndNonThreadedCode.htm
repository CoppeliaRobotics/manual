Threaded and non-threaded script code

Any type of script can run threaded and/or non-threaded.

Non-threaded code

The entrance to a script is always originating from callback functions which are not running threaded, and should not be blocking. This means that every time they are called, they should perform some task and then return control. If control is not returned, then CoppeliaSim will halt.

Non-threaded code is inherently synchronized with the simulation loop:

#python # using sim-2 def sysCall_init(): pass def sysCall_sensing(): print('simulation time:', sim.scene.simulation.time) --lua function sysCall_init() sim = require('sim-2') end function sysCall_sensing() print('simulation time: ', sim.scene.simulation.time) end

Threaded code

Threaded code on the other hand allow running blocking code, without halting CoppeliaSim: the code is in fact preemtively interrupted and later resumed on a regular basis by CoppeliaSim, by default.

Threaded code runs non-blocking (or in non-stepping mode) by default:

#python # using sim-2 def sysCall_init(): pass def sysCall_thread(): while true: print('simulation time:', sim.scene.simulation.time) --lua function sysCall_init() sim = require('sim-2') end function sysCall_thread() while true do print('simulation time: ', sim.scene.simulation.time) end end

This behaviour can be changed via script:setStepping, which then requires explicit yielding via script:step:

#python # using sim-2 def sysCall_init(): sim.self:setStepping(True) # enable the stepping mode (no more preemptive yielding from CoppeliaSim) def sysCall_thread(): while true: print('simulation time:', sim.scene.simulation.time) sim.self:step() # resume in the next simulation step --lua function sysCall_init() sim = require('sim-2') sim.self:setStepping(true) -- enable the stepping mode (no more preemtive yielding from CoppeliaSim) end function sysCall_thread() while true do print('simulation time: ', sim.scene.simulation.time) sim.self:step() -- resume in next simulation step end end

Above while loop now executes exactly once for each main simulation step and does not waste time reading and printing the simulation time over and over for the same simulation step: once the current thread has yielded control back to CoppeliaSim, it resumes in next simulation step.

Several blocking functions are specifically meant to be running from within threaded code, e.g. Motion.MoveToConfig:run or Motion.MoveToPose.run: those functions handle thread yielding for you, at the appropriate time.

Refer also to the stepping mode, to the thread-related and script-related methods and properties.
